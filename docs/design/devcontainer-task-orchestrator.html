03

How you use it

You touch the system twice per task: once to approve what it will attempt, once to review what it produced. Everything between runs without you.

Approval is per task, not per batch. Six tasks are six small reviews, and a skip never stops the rest. After dispatch there is no second gate, so the brief is your last chance to steer. A failure comes back as a status, never as a question.

The shape of /odoo-orchestrator:run: queue now, read later

  1. Read the dead letters first. dispatch.sh dead-letters through orchestrator.py unhandled. Each entry is a task that owes a result. Decide one at a time: re-queue unchanged, amend the brief and re-queue, or drop. Nothing retries itself.
  2. Pull and harden. Read the task and its chatter through the org connector. Write the brief as behaviour and outcome only: no file, module, model, method, command or mechanism. orchestrator.py plan-path mints a draft file, orchestrator.py lint is a backstop, never the approval.
  3. Approve per task. One block per task: approve, revise, or skip. A revise rewrites the brief and dispatches nothing. A re-queued task is approved again like any other.
  4. Submit the approved set as one argument. dispatch.sh add '[{"repo","task","brief"}]' queues the jobs in seconds, starts the dispatcher and webui services in the background and prints {"batch_id","jobs"}. An element can add round and entry. The command records the batch with batch-add, marks the old dead letters handled, tells you the ids and http://127.0.0.1:8765, and ends. It does not wait and does not poll.
  5. Later, read the finished batches. Run the command again with no task ids. orchestrator.sh batches lists the batches not yet read. For each one, dispatch.sh report <batch_id> gives the jobs. orchestrator.py friction appends the batch's friction entries and orchestrator.py records prints its records for import. Dead letters are shown with their cause and detail. Questions on a DONE job become a new brief, approved again, and submitted at round plus one. batch-done closes the batch.

The jobs outlive your session

The dispatcher is a compose service, not a child of your session. If the session ends after add returns, the jobs go on. The dispatcher exits when no job is PENDING or RUNNING, and restart: "no" keeps it down until the next add. It is still not a daemon: it runs only while there is work. The blocking dispatch run call that this section once described is now only the container command of the service. Section 22 (F17) recorded the old limit.

04

Inside one container

One session per job. It starts at the /odoo-dev:implement entry, and the implementer drives the existing stage commands in order. Each stage command keeps its fork and its own agent.

The entry is a plugin command, not a bare agent flag. claude -p "/odoo-dev:implement <task> <brief>" is documented behaviour: a slash command in the prompt string expands before the run, and -p waits for a forked command. The dispatcher no longer passes --agent, because the command names its agent. code lags · F4

The workflow option, preferred when the two checks pass

The chain build → test → iterate → pr is fixed, and a fixed chain is better run by a script than by a model. A plugin workflow at plugins/odoo-dev/workflows/implement.js makes it one: each step is an agent() call targeting the builder, tester and pr agents with the same prompt the commands build, the test-iterate loop and the three-red-runs cap are control flow, and the stage commands are not called at all. It starts the same way, -p "/odoo-dev:implement <task> <brief>", and needs Workflow(odoo-dev:implement) in the allow rules, or dontAsk denies the launch.

Two facts decide which shape ships, and one throwaway -p call checks both: that agent() can target a named plugin agent, and that the allow rule admits the workflow under dontAsk. If both hold, the workflow is the entry and implement.md becomes its launcher. If either fails, the command entry above stays, and the stage calls inside it are verified on the first run. Section 22 lists both checks.

05

The agent never asks, it defers

Two things travel back that are not the diff: questions about the work, and friction with the tools. Neither may stop the run, because nobody is there to answer.

Questions about the work

The agent carries on. It makes the most defensible choice available, records the choice and the question together, and keeps building. Both ride out on the draft pull request beside the diff they affected, and the count comes back in the status. The schema of section 19 makes this structural: assumption and why are required beside every question.

The test for whether to stop

If the agent can name a choice it would defend to a reviewer, it makes that choice and carries on. A genuine stop is an environment failure: the project does not resolve, the stack does not come up, the repository is not there. "I would like this confirmed" is a question, and questions wait for the pull request.

The answer loop

You answer on the draft pull request. The host turns the answers into a new brief of behaviour, takes your approval again, and submits the same task at round plus one. The job signature does not change. The agent finds the existing branch and open pull request in task.json, so it iterates and edits the pull request rather than opening a second one. The global rules file tells an interactive subagent to park and stop. That paragraph is scoped to watched sessions, and the implementer's definition restates the positive rule. The prohibitions in that file stay in force (Appendix A, decision 12).

Friction with the tools

Friction is about the system, never the task. It goes to a dated file in the orchestrator home that you read later to improve the tooling, and it asks nothing. One entry carries four fields: the tool exactly as invoked, what was expected, what happened quoted verbatim, and what the agent did about it. Nothing files an issue automatically.

The test that keeps this honest

If the agent cannot name the command and quote what it printed, there is nothing to report. The empty list is the normal, expected result of a run that went well, and the agent definition says so in those words.

06

Running many at once

One container per project, several sessions inside it. A container is a clean room for agents to work in, not a cell. Postgres and the memory service are shared sidecars for the whole machine, and the host config directory is mounted on purpose.

The agent gets no docker, because it needs none. Every container mounts the host's docker socket so the stack scripts can create the shared sidecars. The implementer is never the thing doing that, so Bash(docker:*) is denied and the guard hook refuses every container runtime. This protects against an accident, not a hostile agent: the one real incident in this research was an agent running devcontainer up and adopting an unrelated project's container.

Each session tests on its own database. run-tests.sh drops <project>_test_<task> by name before it creates it, so two sessions on one task in one project collide without a suffix. The odoo-session-db skill adds a suffix hashed from a session id. The tester agent and /odoo-dev:test carry that skill, and the implementer passes its job id down as the session id, because the tests run in the tester fork and a skill the fork does not have is inert. code lags · F5

Two risks are accepted, not solved. Sibling worktrees share refs, objects and packed-refs, so concurrent commits, fetches and pruning in one repo can collide, and a crash can leave a lock that wedges the siblings. Each worktree has its own index, so the index is not the problem. worktree-ensure.sh locks only its own operations, and nothing in this design adds a lock where the committing happens. The shared config directory can also corrupt under concurrency, because Claude Code itself writes session state there. The symptom is several tasks failing at once shortly after one dies, and the fallback is a private config directory per dispatch. Both stay open until a real failure asks for the fix.

07

The queue

A job is a repo, a task id and a brief. The orchestrator submits a batch in one call. The dispatcher admits each job when the machine has room, and otherwise makes it wait. The queue decides when a job starts, never what it does.

Admission on measured memory

The gate reads MemAvailable from /proc/meminfo and admits when it is at or above MIN_FREE_GB. It never reads free memory, because the page cache counts as used on Linux, and it never counts jobs, because a configured count is wrong on both sides of every interesting case. Admission is serial: measure, admit one job, bring its container up, let the machine settle for DISPATCH_SETTLE_S, then measure again. A read that fails is retried five times, one poll apart, and then ends the run with the job still pending. The gate never admits on a guess.

The gate waits, and nothing evicts for it

The dispatcher does not call stack-ensure.sh, so no eviction sweep runs on its behalf, and a container holding memory for an editor session is never stopped by the queue. If editor stacks keep the machine under the threshold, every job waits. The wait is bounded: after DISPATCH_ADMIT_TIMEOUT_S with nothing admitted, the run ends with exit 1, the jobs stay PENDING, and stderr names the threshold and the figure. Stopping an idle editor stack is a manual step until the first runs have measured real pressure. The ODOO_ACTIVE_REPOS export is removed, because nothing read it. code lags · F7

The job store is on disk

One row per job with a state, persisted in jobs.db, private to the dispatcher, and separate from the run record because mutable working state and write-once evidence have different lifetimes. Persistence buys restart, and restart needs reconciliation: every job marked running at startup is lying, because its process died with the previous dispatcher. Before anything is admitted, each stale running row has its container and worktree inspected, gets a FAILED run row when it had a session id, and becomes an ORPHANED_BY_RESTART dead letter. Skip this and the duplicate gate blocks those tasks forever.

The singleton lock, and a submit that needs none

Two dispatchers would not overload the machine, because both read the same memory figure and both back off. They would corrupt state: both could mark one pending job running, and one could start a container the other is about to stop as idle. So the entry point takes an exclusive whole-file advisory lock on dispatcher.lock before anything else and holds it for the life of the process. The kernel releases it on any exit, including an uncatchable kill, so there is no stale lock. It is a separate file from both databases, because locking a database file collides with the engine's own locking. There is no flag to skip it. Running two means a second state root, which is an explicit act. This holds on a local filesystem only. The singleton is the dispatcher service of the compose project odoo-orchestrator, which dispatch.sh add starts. dispatch dead-letters and dispatch report only read, and dispatch submit only inserts. None of the three takes the lock, so they work while the dispatcher runs, and the running dispatcher admits new rows at its next step.

Containers come up on demand and stop when idle

Two independent idempotent checks at two lifecycle points. On admission: devcontainer up starts or reuses the project's container. On every ending: if the project has no job running and none pending, stop its compose project. Both halves of that predicate, or a finishing job stops a container out from under a sibling mid-test. Stop, never remove, and never touch the shared sidecars. The check races: a job can end, stop the container, and a new job can start it a second later. That costs one restart, which is why there is no lock around it.

08

The job

One call submits as many jobs as you approved. One admitted job renders one up and one exec. Every flag on the command line is there for a reason already verified, or marked as untested in section 22.

The approved set arrives as a single argument, a JSON array, each element {repo, task, brief} with an optional round and an optional entry. The call is dispatch submit, which dispatch.sh add runs. It takes no lock, so it works while a dispatcher runs. There is no batch file, because a dispatch list is a product of one orchestration run and writing one would make the dispatcher own a file format. The brief path is different: the contract is "a path I can read as text". The dispatcher reads it once, at submission. The text goes into the job row and into the prompt, and the path is forgotten. The orchestrator can delete the file at once, and a re-dispatch uses the stored text. The path must resolve in the dispatcher container, which is why the compose file binds every path under the same string as on the host. A path handed into the job container would not resolve. The whole call is validated before anything is written, so one bad element rejects the call and no job of it exists. It exits 2 on a task named twice, on a task that already has a live job, and on a repo with no checkout or no central config. A repo name can start with a dot, and is never . or ... A prompt of more than 120 KB is refused, because one argv string is capped at 128 KiB.

entry is the slash command the prompt starts with. It is one of /odoo-dev:implement and /odoo-dev:upgrade-implement, and it defaults to DISPATCH_ENTRY. It is stored on the job row (the entry column of jobs, SDK migration 2), so a re-dispatch and a report keep it, and the job line of the usage-log names it. The central config for a repo is the single match of <config root>/github.com/*/<repo>/.devcontainer/devcontainer.json. DISPATCH_REPO_OWNER only breaks a tie. Zero matches or several matches dead-letter that one job as CONTAINER_START_FAILED, and the other jobs go on. Each job's bundle is also its ODOO_DEV_STATE_DIR. Before up, the dispatcher copies the repo map (DISPATCH_REPO_MAP_FILE, default ~/.config/odoo-dev/repo-map.json) into the bundle. A missing map dead-letters that job as CONTAINER_START_FAILED with the detail cannot copy the repo map <file> into <bundle>. The order is mark_running, the bundle directory, the repo map, the workspace check, up, the mount assertion, the readiness wait. Each session also gets ODOO_JOB_ID.

The invariants file

The agent definition describes a sequence. This file describes what is true at every moment regardless of where in that sequence the agent is. Commandments, not steps. It ships at plugins/odoo-dev/prompts/unattended-invariants.md.

Two tests for whether a line belongs here

An invariant can be checked at a single moment, without knowing what came before. "Never force-push" passes. "Run the tests after you build" fails and belongs in the definition. A line earns its place only if breaking it is unrecoverable or invisible. A force push is unrecoverable. A fabricated test result is invisible. A clumsy field label is neither.

# standing
You are running unsupervised. No human will answer you.
Never stop to ask. If you can name a choice you would defend to a reviewer, make it, record it with the question, and continue.
Never enter plan mode.

# irreversible
Never force-push, in any variant.
Never mark a pull request ready, approve one, or merge one.
Never push to a default or protected branch.
Never delete a remote branch.

# forbidden routes
Never create a pull request except through the sanctioned script.
Never stream-edit or shell-redirect into a file inside a working tree.
Never commit a module without bumping its manifest version.
Never commit Claude configuration or agent artifacts to a repository.
Never reach Odoo except through the sanctioned server.
Never run docker. Never write to the configuration directory.
Never start or stop a task, and never write a timesheet.

# honesty
Never report a result that is not in a tool's own output.
Never edit code to silence a finding about it.
Never state a number you did not read.

# enforcement
The irreversible and forbidden-route lines above are also refused by the hook unattended-guard.sh. It engages when the environment variable ODOO_UNATTENDED is set to a non-empty value, in this session and in every subagent it forks. A refusal from that hook is final. Never work around it.

A hook refuses the call and a tool rule removes the tool. Both are deterministic and indifferent to how long the session has run. What every run records

The dispatcher holds the clock and the agent is never asked. A session writes one durable row, and that row is the atom the sessionizer groups. Nothing is attributed, so nothing can be misattributed.

started_us, ended_usThe dispatcher's own clock, as integer microseconds. The start is the moment the session process is spawned, and the end is the moment it exits. What this stops capturing

Only dispatched work produces a record. Your own time, reviewing briefs and pull requests and answering questions, produces nothing, because no job wrapped it. If you bill agent runs only, this is correct. If you bill review time, it needs its own deliberate record, not a return to inferring it from tool calls. Settle it before the first invoice built this way.

The run is the event

There is no separate event table. A run is a bounded interval of work on exactly one task, recorded by the process that performed it. The legacy event store reconstructed "when was work happening on what" from tool calls, hooks and branch names, and every heuristic in it exists to recover an intent the signal never carried: an agent reads one task while working on another, the read emits an event, and time bills to the task it merely looked at. The run row cannot have that failure. The event store is therefore deprecated, not repaired (section 20).

The sessionizer still supplies grouping, the floor and rounding. A task touched at nine and again at four is two contexts and two minimums, and the dispatcher feeds that rather than applying a per-task floor of its own.

The persisted state

Specified on merit and built as specified, with the departures the code documents. This is the reference the rest of the repo follows.

Ten rules every store obeys

  1. SQLite, one file per ownership boundary. Two owners never share a file.
  2. Queryable facts are rows; opaque documents are files. A transcript goes on disk and an index row says it is there.
  3. Only state that must survive a run is written down. A dispatch list and a rendered command are not state.
  4. Every table STRICT, every column typed, almost none nullable. Default empty strings beat nulls for "not applicable".
  5. Constraints express the invariants. An impossible combination is a CHECK. A thing that must be unique is an index.
  6. Time is an integer. Microseconds since the epoch, UTC. Three text timestamp shapes parse and do not sort against each other, and a sessionizer that orders by time would then move a bill. Readable forms are virtual generated columns.
  7. Immutable means immutable. Triggers refuse updates and deletes on every write-once table.
  8. One module owns each store. Typed operations and no SQL at a call site.
  9. Migrations are numbered and forward-only. Each a transaction, each recorded, none conditional on the current shape.
  10. An enum value is a complete statement. CONTAINER_START_FAILED reads in a query result at speed; CONTAINER needs a lookup.

    batch_id      TEXT    NOT NULL,

    repo          TEXT    NOT NULL CHECK (repo <> ''),
    round         INTEGER NOT NULL DEFAULT 1 CHECK (round >= 1),
    state         TEXT    NOT NULL CHECK (state IN ('PENDING','RUNNING','DONE','DEAD_LETTER')),
    brief         TEXT    NOT NULL CHECK (brief <> ''),   -- the text read at submission, never the path
    submitted_us  INTEGER NOT NULL CHECK (submitted_us > 0),
    started_us    INTEGER CHECK (started_us IS NULL OR started_us >= submitted_us),  -- admit time
    ended_us      INTEGER CHECK (ended_us   IS NULL OR ended_us   >= started_us),
    session_id    TEXT    NOT NULL DEFAULT '',
    container     TEXT    NOT NULL DEFAULT '',
    worktree      TEXT    NOT NULL DEFAULT '',
    outcome       TEXT    NOT NULL DEFAULT '',   -- the stored run outcome of a DONE job
    dead_reason   TEXT    NOT NULL DEFAULT '' CHECK (dead_reason IN ('', the ten causes of section 18)),
    detail        TEXT    NOT NULL DEFAULT '',   -- raw signals, free text
    submitted_at  TEXT GENERATED ALWAYS AS
                  (strftime('%Y-%m-%dT%H:%M:%fZ', submitted_us/1000000.0, 'unixepoch')) VIRTUAL,
    CHECK (state <> 'PENDING'           OR started_us IS NULL),
    CHECK (state <> 'RUNNING'           OR (started_us IS NOT NULL AND ended_us IS NULL)),
    CHECK (state NOT IN ('DONE','DEAD_LETTER') OR ended_us IS NOT NULL),
    CHECK ((state = 'DEAD_LETTER') = (dead_reason <> ''))
) STRICT;

CREATE UNIQUE INDEX idx_jobs_one_live ON jobs(task_id) WHERE state IN ('PENDING','RUNNING');
CREATE INDEX idx_jobs_state ON jobs(state, submitted_us);

The partial unique index is the strongest control in this document. It makes "one live job per task" a property of the engine. submit inserts and translates the integrity error into a DUPLICATE_TASK_IN_FLIGHT dead letter. It never queries first, because code that queries first and inserts second is wrong under concurrency and looks right in every test.

The envelope has its own table because the sessionizer scans runs constantly and never wants the blob. Store three: the job artifact bundle

Keyed by job, never by session, so a job that failed before a session existed still gets a directory. The agent uploads nothing. The workspace mount

On the compose path the CLI adds no workspace bind mount of its own. Every project config declares "mounts": ["source=${localWorkspaceFolder},target=/mnt/extra-addons,type=bind"], and the variable resolves to the dispatcher's --workspace-folder. Docker answers a missing bind source by creating an empty root-owned directory, so an empty workspace looks exactly like a healthy container.

The dispatcher guards it twice. Before up, the workspace must be a git checkout. After up, docker inspect must show /mnt/extra-addons as a bind of exactly that folder and /usr/local/share/odoo-dev as a bind of the host odoo-dev directory. Then, before exec, postgres must answer and odoo --version must print inside the container, as stack-ensure.sh waits for them. Without that wait, the first job after a cold start can hit an Odoo that is not up. code lags · F11

16

What this is not

  • Not a daemon. You start a batch. Nothing runs on a schedule and nothing watches Odoo on its own. The dispatcher service starts on dispatch.sh add, uses restart: "no" and exits when the queue drains. Only the read-only webui service stays up.
  • Not an auto-merge. The run ends at a draft pull request. Nothing is marked ready, approved or merged without you.
  • Not a general job runner. The queue admits jobs and dead-letters the rest. No automatic retries, no priorities, no lifecycle beyond the four states.
  • Not self-healing. A run that does not return a complete valid object fails, and stays failed until someone looks. Nothing reconstructs a partial or invents a description.
  • Not a self-filing bug tracker. Friction reports accumulate in one file you read.
  • Not an automatic timesheet. Runs are evidence. Turning sessions into billable hours stays a step you take.
  • Not a replacement for the interactive workflow. Typing the stage commands by hand keeps working exactly as it does now.
  • Not the 2026-08-21 design. That put the orchestrator inside a devcontainer. This puts the orchestrator command in your own session, and the dispatcher in a compose service beside it. The host needs only Docker. It supersedes rather than extends.

The dead letter list

A run succeeds when it returns a usable structured value, and not before. Everything short of that lands in one list the orchestrator reads. The cause names where in its own sequence the dispatcher was when things stopped, because it knows that for free.

CauseWhat it means, and the signal already there
DUPLICATE_TASK_IN_FLIGHTRejected at submission by the partial unique index. Nothing ran.
CONTAINER_START_FAILEDdevcontainer up did not succeed, or the readiness wait expired. No session ever existed.
WORKSPACE_MOUNT_INVALIDThe workspace is not a git checkout, or the container came up with the wrong bind at /mnt/extra-addons or /usr/local/share/odoo-dev. The operator action is in the detail: the container was created without the Feature, so stop it and let the dispatcher create it.

STRUCTURED_OUTPUT_UNREADABLEOutput arrived and no result object could be parsed from it.
ORPHANED_BY_RESTARTA stale running record found at startup. Its process died with a previous dispatcher.

The success test is never a status field. A run on this machine returned subtype: "success" and is_error: true in one object. So the test is whether a usable structured value arrived, and the status fields go into the free-text detail with the exit code, the signal number, terminal_reason, the errors list, the turn count and the last forty lines of stderr. The enum stays short and stable so it is worth grouping by.

Nothing is salvaged, and nothing retries itself. No partial result is reconstructed, no description is synthesised. The orchestrator reads each entry and takes one of three choices: re-queue unchanged, amend the brief and re-queue, or drop it and tell you. A dropped entry is marked handled. A re-queued entry is marked handled only after the run that re-queued it returns. A blocked run is not a dead letter: a valid object saying outcome: blocked met its contract, bills, and is read on the pull request.

The run schema

The command line takes a JSON Schema and the harness forces the final turn to be a validated object of that shape, returned as structured_output beside the statistics. The model fills the fields in and does not get to decline.

{
  "type": "object",
  "required": ["summary","outcome","modules","changes","tests","questions","friction"],
  "properties": {
    "summary":   { "type": "string" },                      -- one sentence, the description
    "outcome":   { "enum": ["done","blocked","partial"] },
    "modules":   { "type": "array", "items": { "type": "string" } },
    "changes":   { "type": "array", "items": { "type": "string" } },
    "tests":     { "type": "object", "required": ["ran","passed","failures"],
                   "properties": { "ran": { "type": "integer" }, "passed": { "type": "boolean" },
                                   "failures": { "type": "array", "items": { "type": "string" } } } },
    "questions": { "type": "array", "items": { "type": "object",
                     "required": ["question","assumption","why"], "properties": { … } } },
    "friction":  { "type": "array", "items": { "type": "object",
                     "required": ["tool","expected","observed","did"], "properties": { … } } }
  }
}

Shallow on purpose: deeply nested schemas with many required fields fail more often. The dispatcher checks conformance itself and does not take a billing decision on trust. A blank summary is rejected even though the schema allows it, because the summary is the description a run is billed with, and a run with none is a dead letter by design. A required array can be satisfied with [], which is what an empty friction list means. The statistics are untouched by a schema failure: in the observed failing run every statistic was present and only the object was missing.

Phasing out the event store

Every heuristic in the legacy event store exists to answer a question a completed job answers directly. It is kept read-only for history, stops receiving dispatched work, and is removed once the run record has carried a full billing cycle.

  1. Add the source, remove the agent-side calls. Done for dispatched runs: they write a run row and emit no event. The tracking tools are denied and worktree-ensure.sh skips its start_task call under ODOO_UNATTENDED (section 9).
  2. Run both for a while and compare. The sessions query takes --source events|runs|both. Sessionization groups by time and never sums durations, so two sources describing the same work collapse into one session and cannot bill twice. "Agreement" is: the same work sessionized over runs and over events gives the same windows. code lags · F13
  3. Delete the heuristics for sources that carry explicit ids, scoped by source, never wholesale.
  4. Interactive work moves last. Nothing supplies it a session-to-task mapping today, so it stays on the event store. That is the open question of this plan, not the dispatched path.

Session identity under the merge: a window that holds any run is keyed on the session_id of its earliest run, so events joining or leaving the window cannot move the upload key. A run that ended FAILED marks its window, and whether it bills is decided at upload.
